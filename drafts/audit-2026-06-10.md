# Аудит репозитория agent-market (Hireon)

> Дата: 2026-06-10 · Коммит на момент аудита: `057902f` · Анализ без модификации кода.
> Метод: 4 фазы — Repo Map → Audit → Strategy → Task Plan. Все находки привязаны к file:line.

## Executive Summary

**Общая оценка: B−.** Для соло-проекта в pre-launch фазе кодовая база значительно выше среднего: продуманная защита платёжных edge-cases, серьёзная Docker-изоляция, шифрование конфигов, последовательный authz. Оценку тянут вниз четыре вещи: **(1)** деньги живые (YooKassa в боевом режиме с 22.05), а тестов и CI — ноль, всё проверяется руками на проде; **(2)** контейнеры агентов **не останавливаются при неоплате** — после паузы подписки сервис работает бесплатно и жжёт платформенный OpenRouter-ключ; **(3)** криптоподписки через NowPayments не имеют ни `expires_at`, ни механизма продления — оплатил месяц, пользуйся вечно; **(4)** покупатель может инжектить произвольные env-переменные в свой контейнер, включая `AI_MODEL` поверх платформенного ключа. Топ-3 возможности: дешёвый test-harness на чистых функциях денег (они уже хорошо изолированы), reconciler «статус подписки ⇄ состояние контейнера», и воспроизводимый bootstrap БД (сейчас fresh deploy с чистого клона сломан).

## Repo Map

**Назначение:** маркетплейс готовых AI-агентов (hireon.agency). Покупатель платит (ЮКасса/NowPayments), проходит Setup Wizard, платформа поднимает Docker-контейнер агента на VPS, тот работает 24/7. Phase 0: продаются только собственные агенты платформы (`seller_id = NULL`), сторонние — waitlist/outbound.

**Стек:** Next.js 16 App Router + TS strict, Tailwind v4, Drizzle ORM + PostgreSQL 16, BetterAuth (Telegram Login основной), dockerode → tecnativa/docker-socket-proxy, pino + Telegram-alerter, Python 3.11 агенты на OpenRouter.

**Зрелость:** pre-launch продакшн — один VPS, живые платежи, ~0 активных подписок, активная маркетинг-подготовка.

| Директория | Что там |
|---|---|
| `src/app/api/` | 25 API-роутов: checkout, вебхуки, cron, subscriptions lifecycle, admin/seller |
| `src/lib/` | Ядро: `docker.ts` (деплой контейнеров), `payments/` (2 провайдера за общим интерфейсом), `encryption.ts`, `auth*`, `rate-limit.ts`, `validators.ts` |
| `src/components/` | UI; самые большие файлы репо — лендинг (`MobileLanding.tsx` 836 строк) |
| `agents-src/` | 8 Python-агентов: Dockerfile + main.py + общий `ai_provider.py` + `security-baseline.txt` (CVE-floor) |
| `db/` | `migration.sql` (init) + 14 ручных миграций + seeds |
| `infra/` | nginx, fail2ban, systemd-таймеры (backup + restore-test + recurring cron), security-отчёты |
| `instructions/`, `PROJECT_CONTEXT.md`, `lessons.md`, `todo.md` | Живая операционная документация — реально актуальная |

**Что удивило (хорошо):** плотность защитных комментариев формата «почему», журнал инцидентов в `lessons.md`, таймер **тестового восстановления** бэкапа (`infra/backup/hireon-db-restore-test.timer`) — такое редко бывает и у зрелых команд.

**Что удивило (плохо):** при таком уровне паранойи в вебхуках — полное отсутствие автотестов и дыра в lifecycle-enforcement.

## Audit Report

### High

**H1. Контейнеры не останавливаются при неоплате — бесплатный сервис навсегда.** *(факт)*
Cron при 3 неудачных списаниях (или permanent-fail) ставит `status='paused'` — но только в БД (`src/app/api/cron/yookassa-recurring/route.ts:199-206`). `stopContainer` вызывается единственно из юзерской ручки `/stop` (`src/app/api/subscriptions/[id]/stop/route.ts:42`), `removeContainerArtifacts` — только при удалении аккаунта. Контейнер (телеграм-бот, копирайтер) продолжает работать и тратить платформенный OpenRouter-ключ бессрочно. Гарды в `/start`/`/restart` блокируют лишь *перезапуск* — работающий процесс они не трогают.

**H2. Криптоподписки NowPayments — вечный доступ за один платёж.** *(факт)*
Вебхук `payment.succeeded` не ставит `expires_at` (`src/app/api/webhooks/nowpayments/route.ts:100-111`), recurring-cron фильтрует `payment_provider='yookassa'` (`cron/yookassa-recurring/route.ts:96`), других механизмов продления нет (`nowpayments.ts:259-263` — осознанный no-op «продление вручную», но плана-исполнителя в коде нет). `purchaseType='subscription'` через крипту = бессрочный сервис по цене месяца.

**H3. Инжект произвольных env-переменных покупателем + `AI_MODEL` поверх платформенного ключа.** *(факт)*
`subscriptionConfigSchema` принимает **любые** ключи (`src/lib/validators.ts:85-89`), `validateConfigAgainstSchema` проверяет только наличие required-полей и не отвергает лишние ключи (`src/lib/agent-config-validation.ts:24-57`), `buildEnv` мерджит всё в env контейнера: `{...template, ...userConfig, ...platformAi}` (`src/lib/docker.ts:305`). `platformAi` защищает `OPENAI_API_KEY`/`OPENAI_BASE_URL`, но `AI_MODEL` и `AI_PROVIDER` читаются `ai_provider.py:52-56` — покупатель админского агента выставляет `AI_MODEL=anthropic/claude-opus-...` и жжёт платформенные кредиты по кратной цене. Заодно перетирает любые значения seller `env_template`.

**H4. Ноль автотестов и CI на системе с живыми деньгами.** *(факт)*
`.github/` содержит только `dependabot.yml`; в `package.json` нет test-скрипта; «тесты» — ручные smoke-скрипты (`scripts/smoke-agents.mjs`). При этом самые рискованные места — чистые функции и handlers с богатой матрицей edge-cases (идемпотентность вебхуков, amount-mismatch, status-гарды, `ipInCidr`, HMAC) — идеально тестируемы без инфраструктуры. Отказ от тестов зафиксирован в `PROJECT_CONTEXT.md:67` как осознанный — на момент подключения боевой ЮКассы это решение устарело.

### Medium

**M1. Fresh deploy с чистого клона сломан; схема БД невоспроизводима.** *(факт)*
`docker-compose.yml:56` монтирует `./db/seed.sql` — файла нет в репо. `db/migration.sql` не содержит таблиц `access_requests`, `seller_applications`, `agent_waitlist_signups` и поздних колонок (`waitlist_only`, `fits_for`, `keywords`...) — они существуют только как 14 ручных SQL-файлов, применяемых руками по SSH. Migration-runner отсутствует; `drizzle.config.ts` указывает на неиспользуемый `./drizzle`. Disaster recovery = бэкап + ручная археология. В `lessons.md:19` уже есть инцидент уронившегося прода из-за ручного схема-менеджмента.

**M2. Дубль payout при конкурентных IPN-ретраях.** *(факт)*
Идемпотентность payout — select-then-insert по `providerTransferId` без unique-констрейнта (`src/app/api/webhooks/nowpayments/route.ts:144-165`). Два параллельных ретрая IPN проходят проверку оба.

**M3. Security-профили и сайдкары захардкожены через `image.includes()`.** *(факт, признанный долг)*
`src/lib/docker.ts:56-85, 124-146`: новый агент молча получает слабый профиль (root, rw rootfs), если забыть добавить строку. Уже зафиксировано в `PROJECT_CONTEXT.md:66` — это данные агента, место им в записи `agents`.

**M4. Дублирование role-check бойлерплейта в ~8 роутах.** *(суждение)*
Каждый admin/seller-роут заново делает `getUser()` → select role → сравнение. Сейчас пропусков нет (проверены все 25 роутов), но каждый новый роут — шанс забыть. Просится `requireRole("admin")`.

**M5. Вебхуки/cron — select-then-update без транзакций.** *(суждение)*
Единственная транзакция в проекте — удаление аккаунта (`account/delete/route.ts:208`). Сегодня гонки в основном безвредны, но инварианты держатся на дисциплине, а не на БД. Аргумент за unique-констрейнты и `FOR UPDATE` в денежных местах.

**M6. Rate-limit в памяти процесса.** *(факт, принятое ограничение)*
`src/lib/rate-limit.ts:5` — Map на ноду, сбрасывается деплоем. Для одного VPS с nginx-fallback-зонами — нормально; станет дырой при горизонтальном масштабировании.

### Low

- **L1.** `README.md` — стоковый create-next-app, ни слова о проекте.
- **L2.** `YOOKASSA_WEBHOOK_SECRET` объявлен в compose (`docker-compose.yml:101`), CLAUDE.md и `.env.example`, но кодом нигде не читается — создаёт ложное ощущение, что вебхуки подписаны.
- **L3.** Локальная гигиена: `.env.local.bak-2026-05-11` в корне и `agents-src/ai-support-bot/.env` лежат на диске с секретами (в git не попали — проверено по `git ls-files`).
- **L4.** Мёртвое: `agents.cryptoPlanId` (известно), drizzle-kit как зависимость при ручных миграциях.

### Strengths (что беречь)

- **Платёжные edge-cases:** amount/currency tampering-гарды в обоих вебхуках, идемпотентность с учётом гонки cron↔webhook (`webhooks/yookassa/route.ts:250-259`), terminal-статус `cancelled`, zombie-cleanup, дневной Idempotence-Key, transient/permanent-разделение ошибок ЮКассы.
- **Изоляция контейнеров:** socket-proxy с минимальным API-scope и pinned digest, `CapDrop:ALL` + `no-new-privileges` + readonly rootfs + PidsLimit + swap off, per-subscription сети для сайдкаров, postgres вне агентской сети, платформенный ключ только админским агентам (`docker.ts:292-303`).
- **Auth/web-безопасность:** PKCE, secure cookies, CSP с nonce, CSRF origin-check в middleware, timing-safe сравнения везде, 60-секундное anti-replay окно Telegram, soft-delete guard сессий.
- **Операционка:** ежедневный бэкап + автотест восстановления, fail2ban, security-отчёты в `infra/security/`, `security-baseline.txt` для Python CVE, structured logging + Telegram-алерты с severity.
- **Документация процесса:** PROJECT_CONTEXT/lessons.md — честный журнал с верификацией фактов.

**Зоны облегчённого ревью:** фронтенд-компоненты (~8k строк лендинга/каталога), Python-логика агентов (точечно), юр-страницы, `account/delete` (бегло).

## Improvement Strategy

**Тема 1 — «Биллинг должен управлять рантаймом» (H1, H2).**
Сейчас деньги и контейнеры связаны только на входе (payment-gate в `/start`), но не во времени. Целевое состояние: инвариант — *нет работающего контейнера без подписки в `active`* — поддерживается автоматически. Принцип: reconciliation, не точечные хуки: один cron сверяет статусы БД с фактическим состоянием Docker и приводит к согласию.

**Тема 2 — «Сетка безопасности до рефакторингов» (H4, M5).**
Денежная логика уже факторизована в чистые функции — тесты дешёвые. Целевое состояние: vitest + GitHub Actions (tsc, eslint, tests, build) на каждый push; webhook-handlers покрыты табличными тестами по матрице статусов.

**Тема 3 — «Граница env-конфига» (H3, M3).**
Принцип: контейнер получает ровно `setup_schema`-ключи + seller template + платформенные переменные, ничего сверх. Профили изоляции — данные агента, не строки в `docker.ts`.

**Тема 4 — «Воспроизводимая инфраструктура» (M1).**
Целевое состояние: `docker compose up` на чистой VM даёт рабочее приложение с актуальной схемой. Squash `migration.sql` до текущего состояния прода + договорённость, что каждая миграция попадает и в squash.

**Что осознанно НЕ чиним сейчас:** Redis для rate-limit (один VPS), multi-provider AI fallback (отложено обоснованно), автоматизацию payouts (Phase 0 — ручные), разбиение гигантских лендинг-компонентов (работающая витрина, риск > пользы), Resend/email. M5 — точечно через unique-констрейнты, без глобального рефакторинга.

**Сигналы "done":** CI обязателен и зелёный; на проде нет running-контейнеров с не-active подписками (проверяется reconciler-cron'ом + алерт); чистый клон поднимается одной командой; покупательский config не может добавить ключ вне `setup_schema`.

### Скетчи топ-3

**T4 (reconciler):** в существующий суточный cron добавить фазу: select подписок со статусами `paused|expired|cancelled` и `container_id IS NOT NULL` → `stopContainer()` (paused/expired) или `removeContainerArtifacts()` (cancelled, по продуктовому решению) → пометить `container_id`. Gotchas: `stopContainer` сам пишет `status='paused'` — не дать перетереть `expired`; добавить expired-фазу (`expires_at < now() - grace` → `status='expired'`); алертить список остановленных. Прогонять на VPS на тестовой подписке.

**T2+T1 (тесты):** `npm i -D vitest`; выделить из вебхук-роутов чистую функцию `decideWebhookAction(sub, event) → {action, updates}` и тестировать таблично (заодно T10); чистые функции тестируются как есть. CI: setup-node, `npm ci`, `tsc --noEmit && eslint && vitest run && next build`. Gotcha: `next build` требует env — подложить фейковые.

**T6 (whitelist):** в `validateConfigAgainstSchema` третий массив `unknown[]`: ключи `config` вне `schema[].key` → reject. Применяется во всех путях к деплою автоматически (config/start/restart уже зовут её). Проверить прод-конфиги на легитимные внесхемные ключи; `_meta_*` исключить как в `docker.ts:42-44`.

## Open Questions

1. **Крипто-подписки:** продление через новый invoice руками юзера или отключить `purchaseType='subscription'` для NowPayments до Phase 1 (оставить one_time)? Второе — одна строка в checkout.
2. **Cancelled-подписки:** контейнер стопить или сразу сносить с volume? Вопрос данных юзера.
3. **`expired` после неоплаты:** grace-период до остановки контейнера (0/3/7 дней)?
4. **На VPS существует `db/seed.sql`** вне git? Если да — забрать в репо при T3, если нет — убрать mount.
5. **RTO при потере VPS:** целевое время восстановления? Определяет глубину T3.
